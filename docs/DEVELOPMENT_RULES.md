# Development Rules

## 总则

`v-ui` 后续开发默认遵循：

1. 先审计
2. 再设计
3. 最后编码

禁止跳过前两步直接改主线功能。

## 标准流程

每次开发都必须按这个顺序执行：

1. 安全检查
2. 创建快照
3. 只读审计
4. 设计最小方案
5. 编码
6. `go test ./...`
7. `go build ./...`
8. 真机验证
9. UAT
10. 提交
11. Release 或进入下一轮审计

## 快照规则

每轮开发前必须创建：

- git tag
- backup branch
- `tar.gz` 快照

目的：

- 可回滚
- 可审计
- 可对比

## 分支规则

- 稳定基线分支：`v-ui`
- 新功能分支：`feature/*`
- 备份分支：`backup/*`

禁止：

- 直接在稳定分支上做未审计功能开发
- 跳过验证直接 push

## 变更规则

默认要求：

- 先读现状
- 先确认真实字段与真实调用链
- 先给出封顶线
- 只做最小必要修改

禁止：

- 直接凭印象修改
- 一轮内同时重构前端、后端、安装脚本、运行层
- 在没有 UAT 的情况下宣布功能完成

## 验证规则

每轮编码后至少完成：

- 静态验证
- `go test ./...`
- `go build ./...`

涉及安装、证书、网络、入站、路由、续期等功能时，还必须完成：

- 真机验证
- 真人 UAT

## 发布规则

Release 前必须确认：

- 主线工作区干净
- 文档同步
- 安装路径正确
- 不存在跨项目残留命名
- UAT 通过

如果发现 P0：

- 立即停止发布
- 保留现场
- 先出报告
- 再单独修复

## 禁止事项

禁止：

- 未审计直接改代码
- 未快照直接改代码
- 未验证直接提交稳定基线
- 把 `v-ui` 扩展成多证书平台或多 Provider 平台
- 为了新功能破坏 `x-ui` 运行层兼容

## 目标

所有后续开发都必须围绕同一原则：

- 稳定优先
- 兼容优先
- 最小实现
- 可验证
